Зачем это нужно

Хочется, чтобы у провайдера имён был свой сайт, где человек может ввести Stellar-адрес, подтвердить членство в сообществе или настроить всё, что требуется этому сервису. При этом сайт должен надёжно понимать, какая идентичность Onym к нему обращается. Такой же вход пригодится для кабинета оператора бэкапа и для любого другого сайта, который решит его поддержать.

Предлагаю общий механизм «Войти с Onym» с двумя точками входа: кнопкой на сайте и кнопкой «Открыть кабинет» внутри мессенджера. Сайт получает обычную сессию пользователя, а клиент хранит ключи, подтверждает вход и отдельно работает с результатом — например, принимает запись имени.

Статус: проект спецификации 0.1 · 24 сентября 2026. Этот механизм ещё не реализован и не является утверждённым стандартом Onym. Работающий BSN API и Android PR #263 пока используют прежние подписанные запросы. Все адреса на *.example, новые поля и новые endpoints ниже — проектные примеры.

1. Участники и граница доверия

В предлагаемой архитектуре участвуют четыре стороны:

  • Onym хранит ключ выбранной идентичности и подтверждает владение им.
  • Браузер держит сессию сайта и участвует в переходах между сайтом и сервисом входа.
  • Сайт, или Relying Party (RP), принимает вход по OpenID Connect. Это может быть naming provider, другой оператор или независимый сайт.
  • Сервис входа, или OpenID Provider (OP), проверяет подтверждение из Onym и выпускает стандартный ID Token для сайта.

Для первой версии выбирается архитектура с OP: её проще подключать к существующим OIDC-библиотекам. OP может обслуживать несколько сайтов либо принадлежать одному оператору; обязательного единого сервера для всей сети этот проект не вводит. Каждый сайт явно выбирает, каким issuer доверяет.

Такой выбор имеет цену: OP видит входы и связывает их с идентичностью, а сайт доверяет его утверждениям. Компрометация OP позволяет подделывать вход для доверяющих ему сайтов. Это существенная граница доверия, которую нужно показывать пользователю при подключении сервиса. Вариант с непосредственной проверкой кошелька сайтом требует отдельного профиля совместимости и здесь не определяется.

Для сайта применяется OpenID Connect. OAuth задаёт передачу разрешений, а идентичность сайт получает из проверенного ID Token. Новая часть этого документа — подтверждение ключом Onym между приложением и OP.

2. Что берём из готовых стандартов

Базовый профиль ограничен сайтами с backend/BFF — конфиденциальными OIDC-клиентами. Секреты клиента и токены хранятся на сервере. Чистый SPA, machine-to-machine, offline access и делегирование произвольных действий требуют отдельных профилей.

3. Подключение сайта и провайдера

До первого входа владелец сайта регистрирует у выбранного OP свой client_id, точные HTTPS callback-адреса, initiate_login_uri, название и подтверждённые домены. Адреса с wildcard и произвольный return_url не допускаются. Для v0.1 регистрация административная, с проверкой контроля домена; открытая динамическая регистрация не включена.

RP использует private_key_jwt для собственной аутентификации на PAR и token endpoints: это подпись сервера сайта, отдельная от подписи пользователя. Публичные ключи RP закрепляются при регистрации, секреты сайта никогда не встраиваются в Onym. OP публикует OIDC Discovery и JWKS; RP заранее фиксирует ожидаемый issuer и разрешённые алгоритмы. Адрес issuer из ссылки сам по себе не создаёт доверия.

Для карточки сервиса предлагается добавить в его подписанный манифест следующий блок. Это расширение Onym, которое ещё предстоит реализовать; OIDC не определяет поля этого блока.

"management": {
  "authentication_profile": "urn:onym:auth:oidc:0.1",
  "oidc_issuer": "https://login.example",
  "client_id": "bsn-provider-web",
  "initiate_login_uri": "https://names.example/login/onym",
  "default_target": "https://names.example/account",
  "allowed_targets": ["https://names.example/account", "https://names.example/name"]
}

Onym проверяет подпись манифеста и совпадение этих данных с проверенной регистрацией сайта у OP. Подпись манифеста доказывает владение ключом, поэтому дополнительно нужна проверка домена. В клиенте первый раз показываются сайт, оператор входа и выбранная идентичность. Обычную ссылку в сообщении нельзя автоматически превращать в разрешение на вход.

4. Вход, начатый на сайте

  1. Человек нажимает «Войти с Onym». Backend RP создаёт браузерную транзакцию: случайные state, nonce, PKCE verifier и соответствующий S256 challenge. Они привязаны к короткоживущей pre-login cookie этого браузера.
  2. RP отправляет запрос на PAR endpoint OP и сохраняет параметры у себя. Затем браузер переходит на authorization endpoint с выданным request_uri.
  3. OP проверяет запрос и создаёт challenge Onym, привязанный к данной авторизации и своей браузерной сессии. Показывает «Открыть Onym» либо QR-код для другого устройства.
  4. Приложение получает подписанное описание challenge от доверенного OP, показывает проверенный домен сайта, выбранную идентичность и запрашиваемое раскрытие данных. Пользователь подтверждает вход, после чего Onym отправляет подписанный ответ непосредственно OP.
  5. OP атомарно помечает challenge использованным. Продолжить авторизацию может только браузер с исходной сессией OP. Приложению не выдаются code или токены сайта.
  6. Браузер возвращается на зарегистрированный callback RP с code, state и issuer. RP проверяет связь с собственной pre-login сессией и обменивает code с PKCE verifier и собственной аутентификацией.
  7. После проверки ID Token сайт создаёт новую пользовательскую сессию и перенаправляет на кабинет, очищая адрес от параметров входа.
POST /par HTTP/1.1
Host: login.example
Content-Type: application/x-www-form-urlencoded

client_id=bsn-provider-web&response_type=code&scope=openid&redirect_uri=https%3A%2F%2Fnames.example%2Foidc%2Fcallback&state=STATE&nonce=NONCE&code_challenge=CHALLENGE&code_challenge_method=S256&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer&client_assertion=RP_SIGNED_JWT

В примере используются заполнители, а не исполнимый запрос. Успешный PAR отвечает HTTP 201 с request_uri и expires_in. Следующий браузерный переход выглядит так:

https://login.example/authorize?client_id=bsn-provider-web&request_uri=urn%3Aietf%3Aparams%3Aoauth%3Arequest_uri%3AOPAQUE

Параметры PAR, обработка ошибок и аутентификация клиента следуют RFC 9126. Verifier остаётся на backend RP; пример запроса к token endpoint:

POST /token HTTP/1.1
Host: login.example
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=ONE_TIME_CODE&redirect_uri=https%3A%2F%2Fnames.example%2Foidc%2Fcallback&client_id=bsn-provider-web&code_verifier=VERIFIER&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer&client_assertion=FRESH_RP_SIGNED_JWT

5. Вход, начатый из Onym

В карточке подключённого сервиса пользователь нажимает «Открыть кабинет». Onym открывает в системном браузере зарегистрированный initiate_login_uri сайта. Для запуска используется Third-Party Initiated Login из OIDC: адрес issuer и разрешённая целевая страница передаются как параметры запуска.

https://names.example/login/onym?iss=https%3A%2F%2Flogin.example&target_link_uri=https%3A%2F%2Fnames.example%2Faccount

RP проверяет issuer по своему списку доверия и target по точному списку разрешённых адресов. Дальше RP создаёт новую браузерную транзакцию и выполняет тот же Authorization Code Flow с PAR и PKCE, что описан выше. Это обеспечивает одинаковую проверку входа независимо от того, где человек нажал кнопку.

Для привязки к выбранной в приложении идентичности в v0.1 допускается дополнительный непрозрачный login_hint, заранее выданный OP после аутентификации приложения. Он ограничен issuer, client_id, выбранной идентичностью и сроком 60 секунд; не содержит открытого ключа в URL. OP должен отвергнуть вход другой идентичностью при таком hint либо запросить явный выбор заново. Получение hint — опциональная часть расширения, отдельный endpoint которой не стандартизуется в базовой версии.

Hint не разрешает вход и не переносит сессию. Его утечка не должна позволять получить ID Token. Без реализации hint приложение открывает обычный вход с явным выбором идентичности; обещать автоматическое сохранение выбора в таком режиме нельзя.

Когда в этом браузере уже есть подходящая подтверждённая сессия OP и ранее выданное согласие для того же сайта, можно закончить вход без дополнительных действий. При первом входе, другой идентичности, новых разрешениях или требовании свежего подтверждения клиент показывает экран подтверждения. Если без диалога закончить вход нельзя, возвращается соответствующая OIDC-ошибка либо запускается интерактивный сценарий; prompt=none не создаёт согласие.

Кнопка в приложении не гарантирует вход в одно нажатие в новый браузер без существующей сессии. Чтобы дать такую гарантию, понадобится отдельно проверенный механизм привязки приложения к принимающему браузеру. Передавать готовую сессию или входной bearer-код в обычной ссылке базовый профиль не разрешает.

6. Подтверждение идентичности Onym: новое расширение

Участок OP ↔ Onym предлагается определить как urn:onym:auth:key-proof:0.1. Он применяется внутри этапа аутентификации OP и не является новым OAuth grant. Веб-сайт не обязан реализовывать этот участок, если пользуется готовым OP.

OP хранит неизменяемую транзакцию с issuer, client_id, точным redirect_uri, scope, nonce, challenge PKCE, временем создания, браузерной сессией и случайным challenge. Статусы: pending → approved или denied/expired; после approved возможна единственная выдача code. Повторная подпись, параллельный запрос и повторная выдача обрабатываются атомарно.

В ссылку открытия приложения или QR помещается только случайный request_id (не менее 256 бит) и идентификатор заранее доверенного issuer. Статус и токены нельзя получать по одному request_id. Приложение само строит адрес endpoint из проверенных метаданных OP; URL из QR не становится произвольной целью HTTP-запроса.

Предлагаемый endpoint OPНазначение
GET /onym-auth/requests/{id}Получить подписанный JWS challenge; Cache-Control: no-store, лимиты запросов. Никаких токенов и информации о выбранном пользователе.
POST /onym-auth/responsesПередать JWS-подтверждение владельца ключа. Успех: HTTP 204; секрет браузерной сессии не возвращается.

GET возвращает Compact JWS с защищённым заголовком typ=onym-auth-request+jwt, alg=ES256 и kid из заранее доверенного JWKS OP. Пример payload:

{
  "iss": "https://login.example",
  "aud": "urn:onym:authenticator",
  "request_id": "RANDOM_256_BIT_ID",
  "client_id": "bsn-provider-web",
  "rp_origin": "https://names.example",
  "redirect_uri": "https://names.example/oidc/callback",
  "scope": "openid urn:onym:scope:signing-key",
  "oidc_nonce": "RP_NONCE",
  "code_challenge": "RP_S256_CHALLENGE",
  "code_challenge_method": "S256",
  "challenge": "RANDOM_256_BIT_CHALLENGE",
  "interaction": "fresh-key-proof",
  "display_code": "482951",
  "iat": 1800000000,
  "exp": 1800000120
}

Здесь и далее timestamps иллюстративные. Название сайта выводится только из проверенной регистрации OP; rp_origin должен соответствовать зарегистрированному callback. Приложение проверяет issuer, тип, алгоритм, подпись, обязательные поля, срок и соответствие локальному намерению пользователя. Ссылки на произвольные jku/x5u из заголовков не загружаются.

Пользователь видит: «Войти на names.example с идентичностью …», оператора входа и список раскрываемых данных. Для QR-входа оба устройства показывают короткий код сравнения, созданный OP для этой транзакции, и требуют явного подтверждения. OP включает в подписанный request поле display_code: случайную строку из шести десятичных цифр, которая одновременно показывается в исходном браузере и приложении. Этот код не является OTP и не принимается как доказательство входа. Код помогает сопоставить экраны, но сам по себе не защищает от пересланного злоумышленником QR.

Onym формирует отдельный Compact JWS. Защищённый заголовок содержит typ=onym-auth-proof+jwt, alg=EdDSA и публичный jwk с kty=OKP, crv=Ed25519, x=base64url(32 байт ключа). Поле d запрещено. Пример payload:

{
  "iss": "onym:key:<64 lowercase hex characters>",
  "sub": "onym:key:<same public key>",
  "aud": "https://login.example",
  "client_id": "bsn-provider-web",
  "request_id": "RANDOM_256_BIT_ID",
  "request_hash": "BASE64URL_SHA256_OF_EXACT_REQUEST_COMPACT_JWS",
  "challenge": "RANDOM_256_BIT_CHALLENGE",
  "decision": "approve",
  "iat": 1800000020,
  "exp": 1800000110,
  "jti": "FRESH_RANDOM_256_BIT_ID"
}

Подписывается стандартный JWS signing input: base64url(protected-header) + "." + base64url(payload). Пересортировка JSON после подписи не выполняется. request_hash — SHA-256 ASCII-байтов исходного Compact JWS запроса OP, включая его подпись, с base64url без padding. Это связывает ответ со всем показанным запросом и его scope. Используется существующий Ed25519 signing key идентичности Onym; ключи BLS и inbox для входа не используются.

Тело POST — {"proof":"COMPACT_JWS"}. OP декодирует x ровно в 32 байта, выводит из него onym:key: с hex, требует совпадения iss/sub и проверяет Ed25519-подпись. Далее проверяет точное aud, client_id, request_id, challenge, request_hash, decision, срок и свежий jti. Публичный JWK здесь является проверяемым ключом пользователя; его присутствие не позволяет подтвердить другую, уже зарегистрированную идентичность.

Разрешённые decision: approve и deny. Отклонение с выбранной идентичностью подписывается тем же способом; закрытие приложения без выбора приводит к тайм-ауту. Для отказа до выбора ключа приложение ничего не подписывает. Некорректный или просроченный ответ получает HTTP 400 с общим кодом invalid_authentication_response, лимит — HTTP 429. Повтор уже использованного request_id тоже отклоняется.

Предлагаемые пределы: request — 120 секунд, proof — до 90 секунд и не дольше request, code — 60 секунд, ID Token — 5 минут. Допуск часов для проверки iat — 30 секунд; истёкшие challenge и code не принимаются. Размер JWS ограничен 16 КиБ. Неизвестные typ/alg, дубли ключей JSON и критические неподдерживаемые заголовки отклоняются. Кэш replay хранится как минимум до exp плюс допуск часов.

7. Что получает сайт и как хранится сессия

OP подписывает ID Token собственным ключом ES256. Подпись пользователя остаётся между приложением и OP; для неё и ID Token используются разные типы сообщений, ключи и процедуры проверки. Сайт применяет OIDC-библиотеку и проверяет подпись по закреплённому issuer/JWKS, iss, aud, azp при необходимости, exp, iat, nonce, а также auth_time при запросе свежего входа. Идентификатор локального аккаунта — пара (iss, sub).

RP хранит state, nonce, verifier и выбранный issuer в серверной pre-login сессии. На callback должны одновременно совпасть state и её браузерная cookie. Code обменивается только один раз, для того же client_id и redirect_uri. Проверка iss в callback выполняется до обмена токенов. Привязка PKCE к конкретной транзакции описана в RFC 7636, защита от смешения issuer — в RFC 9207.

После входа RP заменяет идентификатор сессии. Cookie кабинета — Secure, HttpOnly, SameSite=Lax, Path=/, без Domain; рекомендуется префикс __Host-. Изменяющие состояние действия защищаются CSRF-токеном и проверкой Origin. В выбранном профиле callback использует GET/query; настройка cookie должна проверяться вместе с этим режимом. Сторонние ресурсы на странице callback не загружаются.

OAuth-токены остаются в backend/BFF. В браузерных localStorage, URL и логах им места нет. ID Token не принимается как разрешение вызывать API. В v0.1 не запрашиваются refresh token и offline_access; сроки собственной сессии сайта задаются отдельно и не продлеваются одним наличием старого ID Token.

8. Идентичность, разрешения и приватность

По умолчанию сайт запрашивает только openid и получает стабильный pairwise sub для своего зарегистрированного сектора. Его OP формирует через секретное отображение либо HMAC с отдельным серверным секретом; простой хеш публичного ключа не скрывает связь. Стабильность отображения и резервирование серверного секрета обязательны, иначе после перезапуска появятся другие аккаунты.

Для naming provider нужен настоящий signing public key Onym, чтобы выпустить запись именно для этой идентичности. Предлагается дополнительный scope urn:onym:scope:signing-key и claim urn:onym:claim:signing-key со значением onym:key:<hex>. Это новые поля данного профиля; пользователь отдельно разрешает раскрытие. OP включает claim только при таком согласии и подтверждённом владении ключом. Профиль требует свежего key proof при первом раскрытии.

Обычный сайт может обходиться pairwise sub. Получивший глобальный ключ провайдер способен сопоставлять его с публичными записями Onym; пользователю это объясняется до входа. Сам OP видит общую идентичность даже при pairwise sub. Имя, аватар и подтверждение реальной личности не следуют автоматически из владения ключом.

Вход не выдаёт право читать чаты, создавать бэкапы, подписывать транзакции Stellar или менять состав групп. Новые API-разрешения потребуют отдельных scopes, ресурсов и согласия. Удаление ключа из Onym также не завершает автоматически уже существующие сессии сайтов.

9. Как это работает с провайдером имён

Настройка на сайте завершается сохранением параметров у провайдера. После возвращения в Onym клиент самостоятельно запрашивает результат через API подключённого провайдера, проверяет его и предлагает пользователю принять имя. Этот порядок обязателен для описанного здесь сценария.

  1. Человек подключает naming provider в Onym и нажимает «Открыть кабинет». Клиент сохраняет, для какого провайдера и какой идентичности начата настройка.
  2. После входа сайт получает разрешённый signing-key claim, связывает его с текущей сессией и показывает собственную форму настройки.
  3. Для BSN пользователь вводит Stellar-адрес и подписывает необходимую транзакцию своим кошельком. Провайдер независимо проверяет данные Stellar, включая связь с публичным ключом Onym, и сохраняет параметры для этой идентичности.
  4. Сайт показывает «Вернуться в Onym». Ссылка возврата только открывает приложение и экран подключённого провайдера. Она не передаёт имя для принятия, токен сессии или доказательство права на имя. Необязательный непрозрачный идентификатор операции служит только подсказкой для поиска сохранённой настройки и не даёт доступа к ней.
  5. После возвращения клиент обращается к API ранее подключённого провайдера от имени той же идентичности. В существующем BSN-профиле он выполняет подписанный запрос request-issuance, используя сохранённую настройку. Провайдер проверяет подпись и принадлежность настройки этой идентичности, повторно проверяет условия выдачи и возвращает подписанную запись имени. Способ передачи ссылки на сохранённую настройку определяется версией API провайдера; браузерная сессия не заменяет подпись запроса.
  6. Клиент проверяет подпись провайдера по доверенному ключу подключённого сервиса, соответствие записи выбранной идентичности, срок действия и остальные требования протокола имён. Адрес API и ключ проверки берутся из данных подключённого провайдера, а не из параметров ссылки возврата.
  7. Onym показывает проверенное имя, источник, идентичность и последствия публикации. Пользователь отдельно подтверждает принятие этой конкретной записи; клиент формирует подписанное acceptance по протоколу имён. Только после успешного завершения принятия имя становится доступным для отображения согласно настройкам клиента.

OIDC-сессия разрешает работу с кабинетом и сохранение настроек. Она не заменяет подписанный запрос на выпуск имени и не даёт сайту права подписывать acceptance за пользователя. Вход, настройка на сайте и принятие имени остаются отдельными действиями с отдельными проверками.

На мобильном устройстве возврат реализуется через зарегистрированную приложением HTTPS-ссылку: Android App Link или iOS Universal Link с подтверждённой связью домена и приложения. Клиент должен поддерживать её обработку. Домен такой ссылки относится к клиенту, а адрес возврата выбирается из заранее разрешённых адресов; сайт провайдера не получает возможность назначать произвольный обработчик. Если приложение не установлено или браузер не открыл его, страница возврата объясняет, как открыть Onym вручную. Если кабинет открыт на другом устройстве, ссылка не запускает приложение на телефоне удалённо: пользователь открывает его сам.

Возврат по ссылке не является обязательным условием получения результата: пользователь может открыть Onym вручную и нажать «Проверить имя» у провайдера. Повторное открытие ссылки не должно автоматически принимать или публиковать имя. Если настройка ещё не завершена, проверка не пройдена или запись истекла, клиент показывает состояние и предлагает повторить запрос либо открыть кабинет; текущее принятое имя не заменяется непроверенными данными. При другой активной идентичности клиент предлагает переключиться на ту, для которой начата настройка.

В мессенджере остаются общие действия: подключить провайдера, открыть кабинет, получить и проверить записи, принять имя, выбрать отображаемое имя и отозвать принятие. Поля Stellar, заявки сообщества и прочая специфика остаются на сайте. Отзыв имени, отключение провайдера в клиенте и выход из кабинета — три отдельные операции.

В экспериментальной версии BSN поддержаны сохранённые настройки, подписанный configuration-status и request-issuance с useSavedConfiguration:true. После возврата Onym Web Preview проверяет состояние и предлагает принять запись; встроенный экран BSN основной версии сохранён.

10. Защита двух сценариев

Ссылки и QR открывают только процесс подтверждения. Они не содержат готового входного билета. Для другого устройства пользователь должен видеть, что разрешает вход в браузер на другом устройстве, проверить домен и сопоставить код. Автоматическое подтверждение QR и присланных ссылок запрещено. Даже сопоставление кода не устраняет социальную инженерию, когда человек сознательно подтверждает чужой сеанс; это ограничение следует учитывать при оценке риска. Подробный разбор таких атак приведён в RFC 10027.

QR в нашем сценарии — способ открыть challenge во время обычного OIDC-входа. Это не реализация Device Authorization Grant. Если понадобится отдельный режим для устройств с ограниченным вводом, он должен следовать RFC 8628, включая device_code, user_code, интервалы опроса и ошибки; переименовывать собственный endpoint в этот grant нельзя.

  • App links привязываются к проверенному HTTPS-домену средствами Android/iOS. Web-клиент получает запрос через отдельный доверенный HTTPS origin. Custom URI scheme в базовую версию не включается.
  • Любой challenge показывается только после проверки JWS OP и регистрации сайта. Клиент не предоставляет сайту универсальную функцию подписания произвольных байтов.
  • OP продолжает вход только для исходной браузерной сессии; polling требует её cookie и same-origin проверки. Наличие одного request_id не даёт наблюдать результат или забирать code.
  • Неизвестные issuer не подключаются автоматически. Discovery и JWKS загружаются с HTTPS, с лимитами, без непроверенных redirects; на сервере исключаются SSRF и запросы в частные сети.
  • Ключи OP могут ротироваться с периодом совместимости. Сайт не принимает key URL из произвольного токена и не меняет ожидаемый алгоритм по входным данным.
  • Логи редактируются: code, подписи, токены, cookies, verifier и идентификаторы входных транзакций не записываются. На страницах входа нет аналитики и внешних ресурсов; Referrer-Policy: no-referrer, Cache-Control: no-store, CSP с запретом framing.

11. Выход, отзыв и смена ключа

«Выйти» завершает сессию текущего сайта. Выход из OP может быть отдельным действием через OIDC RP-Initiated Logout с заранее зарегистрированным post_logout_redirect_uri. Завершение одной сессии не обещает немедленно завершить остальные; массовый выход потребует реализованного распространения logout-событий.

В приложении нужен список разрешённых сайтов: issuer, домен RP, используемая идентичность и выданные scopes. Отзыв согласия прекращает будущий бесшумный вход и последующую выдачу новых разрешений у OP, но уже созданная RP-сессия существует до завершения или отдельного уведомления об отзыве.

В v0.1 восстановление той же идентичности означает восстановление того же ключа. Новый ключ создаёт другую идентичность. Перенос локального аккаунта сайта допускается только через отдельную процедуру, подтверждённую старым и новым ключами либо заранее установленным механизмом восстановления; одинаковое отображаемое имя для этого недостаточно.

12. Что предстоит реализовать и проверить

Первый совместимый комплект состоит из OIDC-сервера с расширением проверки ключа Onym, клиентского экрана подтверждения, app links, регистрации RP, интеграции сайта и общего раздела провайдеров в мессенджере. Нужен готовый проверяемый OIDC-компонент с поддержкой PAR и PKCE; самостоятельную реализацию всего OAuth-сервера этот документ не предлагает.

Перед выпуском необходимы тесты двух точек входа, входа с другого устройства, выбора нескольких идентичностей, отказа, тайм-аута, повторной подписи, параллельного погашения, неверного aud/iss/nonce/state, подмены redirect URI, отсутствующего PKCE, подмены scope, смены OP и утечки QR. Отдельно проверяются login CSRF, фиксация сессии, ротация ключей и отказ сайта после уже подтверждённого входа.

Открытые задачи для следующей версии: полностью определённый API непрозрачного login_hint, доказуемая привязка нового браузера к запуску из приложения для входа в одно действие, распространение отзыва сессий и вариант без посредника OP. До их решения реализация должна честно показывать подтверждение там, где не может безопасно завершить вход автоматически.

Документ остаётся проектом протокола. Экспериментальная реализация доступна в Onym Web Preview и кабинете BSN; она требует явного подтверждения каждого нового входа и не реализует все расширения проекта. Основной веб-клиент и его хранилище не заменяются preview-версией.
